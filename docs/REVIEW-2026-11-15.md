# Repository and Product Review

Reviewed November 15, 2026. Scope: current working tree, Git-tracked files and locally reachable history, configuration, runtime boundaries, tests, dependency advisories and documented feature state. README was deliberately left untouched. No Yahoo requests, league mutations, commits, pushes or deployment were performed during this review.

## Overall judgment

This is a useful, substantial local prototype with sensible foundations. React/TypeScript, a small Python API and SQLite are proportionate to one private league. Fetching, normalization, storage and pure calculations are separated; cached interaction is the right design. It is not yet a production-ready hosted service or a fully reconciled statistical authority.

The next phase should emphasize correctness, reproducibility and private-release operations rather than adding more screens. The principal product risk is data interpretation/accuracy, followed by the missing hosted security and durability model. The principal maintainability risk is growth of the orchestration module and layered CSS overrides.

## Engineering assessment

The folder boundaries are appropriate. Keep backend, frontend, scripts, tests, active concept references, docs and ignored runtime state separate. A root package.json is unnecessary; frontend commands intentionally run from frontend/. The archive is local reference material, not a runtime dependency.

The pure calculation modules and mocked tests are a strength. SQLite durability, stored import progress, separated current/credited semantics and explicit missing-value treatment are also good decisions. No extra queue, ORM, microservice or hosted database is needed for local use at this scale.

Remaining improvements are substantive, not cosmetic:

1. Add CI that installs dependencies into a fresh environment and runs build/tests. Pin/lock Python transitives or maintain a tested constraints file; top-level pins alone do not fully reproduce the environment.
2. Add automated frontend interaction tests for mode/period/filter combinations and browser smoke tests for startup/restart. Existing visual checks are manual, not a regression suite.
3. Add explicit API response contracts and validation. TypeScript types do not validate JSON arriving from Python; current server endpoints return dictionaries rather than fully modeled response schemas.
4. Split the growing service orchestration by import responsibility when next changing it. Consolidate/split the large CSS file and remove superseded overrides with screenshot comparisons. Avoid a broad architectural rewrite during this stopping-point audit.
5. Bound/prune in-memory raw-response caching, measure dashboard payload size/latency, and revisit mounting all views if the league history grows. Define an agreed performance target; a fast laptop is not a benchmark.
6. Add deliberate, tested schema migration and backup/restore procedures before moving the cache to a host. Current additive table creation is sufficient for this prototype but is not a complete migration system.
7. Strengthen import coverage metadata and refresh policy for recent stat corrections and historical weeks. A completed import and a verified result are separate claims.

## Security and privacy judgment

For local use, the important boundaries are present: Yahoo credentials stay on the backend; servers bind to loopback; refresh uses one coordinated worker; requests are GET-only upstream with pacing, timeouts, retry/backoff and persisted counters; SQL uses bound parameters; React renders text rather than raw HTML; responses use no-store; and arbitrary browser-origin refresh posts are rejected.

These controls do not authenticate a user. Anyone/process with authorized local-machine access can read local files and call the local API. The dashboard necessarily sends team/player identifiers and league data to its browser. Git ignore is not encryption and does not secure a copied database or backup. External player images also result in requests to Yahoo's image infrastructure.

Do not expose Vite or this API publicly. A hosted release needs member authentication/authorization, HTTPS, protected secret storage, durable serialized OAuth refresh ownership, persistent storage, coordinated jobs, backups and recovery, plus deployment-specific security testing. There is no adoption of a hosting provider in this repository.

Current source privacy was improved, but historical identifiers remain. If a strict no-league-data public history is required, plan a separate history-cleaning/public-export procedure; do not force-push or erase history casually. No configured credential leak was found, so this audit does not establish a need for emergency credential rotation. Review active mockup images and owner README separately before a public source release. Fan-art assets/branding are not proof of licensing or endorsement; review distribution rights before public release.

## Feature and implementation judgment

Home and Standings are functional with Yahoo data, current-week scores, daily trends, records and sortable completed-week analytics. They are not continuously polled live feeds. Biggest Comeback is limited to reconciled coverage, not a proven full-season maximum. Adjustable comparisons/charts remain limited.

Players has a functional explorer, shared production columns, search, availability/NHL/roster/position filters, player cards and saved recent windows. Coverage is the imported player pool, not every NHL player. VORP and historical rank/roster trends are not implemented.

Rosters offers current-strength and reconstructed credited comparison views, totals/averages, F/D/G analysis and period filters. Current means current players' full period production, even before acquisition. Credited means starting-lineup production while on that team, including former contributors, excluding bench/IR. All 47 closed dates were imported. All 752 daily team checks match, while 35 of 96 completed team-week scores differ from refreshed Yahoo weekly scorecards. This is the highest-priority correctness issue; the visible discrepancy status must remain. Do not force totals to match by distributing unexplained adjustments.

Transactions has completed-season history, manager filters, pagination, completed waiver awards, pickup production, retrospective draft value and post-trade production. Pickup/trade totals are not starting-lineup credit. Trade production continues after later moves, and draft value is descriptive rather than a projection. Competing waiver offers/historical priorities are not available in the sampled feed. Acquisition/Fowler coverage deserves a focused reconciliation before stronger claims.

History has real current-season standings but historical seasons and brackets remain demo content. Six-year history is not delivered; actual keys, access, manager identity and scoring comparability still require validation.

Editorial has manual monthly rankings and saved, dated DRAKE editions with movement. Local publishing works; any scheduled Codex automation is external to the repo and was not independently checked in this audit. This is not a self-contained hosted AI publishing service.

Mobile layouts have been checked at selected sizes, but there is no device/accessibility regression matrix. Wide tables still scroll horizontally. No dedicated screen-reader/keyboard audit or formal accessibility conformance claim is warranted yet.

## Recommended next sequence

1. Accuracy: resolve weekly discrepancies; reconcile pickup acquisition intervals and verify correction refresh behavior. Define a small set of golden team/week/player examples checked against Yahoo.
2. Reliability: CI, clean installs, response contracts, frontend tests, coverage/staleness UX and a private backup/restore drill.
3. Requested depth: validated historical seasons/manager mapping; adjustable comparisons; then player rank trends, VORP, trade evaluation/polls and scoring scenarios.
4. Private release: decide access/hosting and operational ownership, then build and verify deployment security and durability. Recheck provider limits at that time; no free-tier promise was made here.
5. Later integrations: Discord/MCP after shared metric definitions are stable; do not make another service depend on this laptop running.

The owner-written TODO priorities remain the product source of truth. This sequence reflects risk and dependencies, not a replacement feature specification.
